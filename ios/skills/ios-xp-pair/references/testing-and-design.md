# 테스트와 단순한 설계

## 동작을 입증하는 가장 저렴한 테스트 선택하기

| 확인할 질문 | 우선 사용할 피드백 |
|---|---|
| 검증, 형식 변환, 상태 전이가 동작하는가? | Swift Testing 단위 테스트 |
| Client가 전송 데이터와 실패를 올바르게 변환하는가? | 통제된 경계를 사용하는 단위 또는 통합 테스트 |
| 화면이 Loading, Content, Empty, Error, Dark Mode, 큰 글씨를 지원하는가? | SwiftUI Preview와 접근성 검사 |
| 사용자가 중요한 여러 화면의 흐름을 완료할 수 있는가? | XCUITest |
| Apple Framework가 실제 Hardware나 Entitlement에서 동작하는가? | 집중된 Adapter 테스트와 실기기 검증 |

기존 Target에서 XCTest가 필요하거나 UI·성능 테스트를 작성할 때는 XCTest를 사용한다. 새 API를 가르치기 위해 테스트 Framework를 바꾸지 않는다.

## 화면에서 시작해 동작 모델로 내려가기

Story의 첫 접점은 사용자가 진입하고 행동할 화면이다. 최소 UI와 관찰할 상태를 먼저 세운 뒤, 화면을 동작시키는 비즈니스 결정과 상태 전이를 `View.body` 밖의 모델로 밀어낸다. 불가능한 조합을 허용하는 여러 Boolean보다 상호 배타적인 Case를 가진 명시적 상태를 사용한다. 변경 가능한 상태의 단일 Source of Truth를 유지하고 가능하면 표시할 값을 계산해서 만든다.

화면 동작을 따라가며 실제로 필요해질 때 Networking, Persistence, 시간, 알림, CallKit, Audio 같은 시스템 경계에 Protocol, Closure 의존성, Adapter를 도입한다. Story가 그 경계의 실제 동작을 요구하면 production Adapter까지 같은 수직 슬라이스에 연결하고 경계에 맞는 통합 테스트나 실기기 검증을 수행한다. 모든 Type에 Interface를 만들지 않는다. 테스트는 구현 세부 사항을 재현하는 대신 결과가 일정하지 않은 협력 객체를 통제해야 한다.

## 레드-그린-리팩터의 근거

- **레드:** 집중해서 실행한 명령을 기록하고, Fixture나 Build 설정이 망가져서가 아니라 동작이 빠졌기 때문에 실패했는지 확인한다.
- **그린:** 예제를 만족하는 가장 작은 운영 코드 변경을 선택하고 해당 테스트를 실행한다.
- **리팩터:** 테스트가 통과하는 동안 중복을 제거하고 이름이나 소유권을 단순하게 만든 뒤 관련 테스트 묶음을 다시 실행한다.

실행 가능한 Test Target이 아직 없다면 첫 화면 수직 슬라이스를 시작하는 데 필요한 최소 준비 작업으로 테스트 기반을 만든다. 이를 사용자 Story로 바꾸거나 테스트 기반만 만든 채 슬라이스를 끝내지 않는다. Xcode 프로젝트 변경에 GUI 작업이 필요하면 Target과 Target Membership 변경을 설명하고 명시적으로 검증한다.

## XP 설계 점검

기능 단위를 마치기 전에 다음을 확인한다.

- 기능의 언어로 동작을 표현했는가?
- Story가 사용자의 화면 행동에서 시작하고 관찰 가능한 화면 결과로 끝나는가?
- 필요한 저장소·외부 서비스·Apple API까지 하나의 production 경로로 연결했는가?
- 실제 Backend나 권한이 필요한 Apple 서비스 없이 기능을 테스트할 수 있는가?
- 변경 가능한 상태의 소유자가 하나로 명확한가?
- 현재 필요한 유연성만 구현했는가?
- 학습자가 다음 안전한 변경을 설명할 수 있는가?

`plan.md`를 이 저장소의 설계와 커리큘럼 맥락으로 사용한다. 현재 동작에 실제로 필요하지 않다면 뒤 주차의 기반 구조를 앞선 Story에 억지로 넣지 않는다.
