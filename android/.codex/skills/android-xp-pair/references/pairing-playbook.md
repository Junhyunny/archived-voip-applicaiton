# 페어링과 인에이블먼트 운영 지침

설명의 양, 제어권을 사용자에게 돌려줄 시점, 막힌 초보자를 도울 방법을 결정할 때 이 문서를 사용한다.

## 교수 순환

한 번의 대화 순환을 짧게 유지한다.

1. **방향 잡기:** 현재 행동을 이름 붙이고 관련 파일이나 경계를 가리킨다.
2. **생각 끌어내기:** 단순 지식 확인이 아니라 유용한 사고 모형을 드러낼 때만 예측을 요청한다.
3. **실행하기:** 현재 드라이버가 작고 눈에 보이는 변경 하나를 수행한다.
4. **관찰하기:** 의미 있는 가장 좁은 검사를 실행하고 결과를 함께 읽는다.
5. **설명하기:** 결과를 안드로이드 개념 하나와 연결한다.
6. **전이하기:** 같은 개념을 가까운 다른 사례에 사용자가 적용하게 한다.

답하지 않은 질문을 여러 개 쌓지 않는다. 사용자가 막혔다면 다시 움직이기에 충분한 도움을 제공한다.

## 개입 단계

필요한 만큼만 아래 단계로 내려간다.

1. 목표를 다시 말하고 관련 심볼을 가리킨다.
2. 범위를 좁히는 질문이나 개념 힌트를 제공한다.
3. 작은 의사 코드 형태나 테스트 이름을 알려준다.
4. 결정 하나를 사용자의 몫으로 남긴 부분 구현을 보여준다.
5. 변경을 직접 시범 보이고 검증 근거를 설명한다.

막힘이 해소되면 제어권을 사용자에게 돌려준다. 완전한 초보자에게 문법 기억을 억지로 요구하는 일은 대체로 유용하지 않다. 아키텍처, 상태 소유권, lifecycle과 테스트 경계에 관한 고민이 더 중요하다.

## 다른 상황에도 적용되는 설명

다음과 같은 짧은 형태를 사용한다.

```text
문제: 어떤 관찰 가능한 문제를 해결하는가?
소유자: 어떤 객체가 이 상태나 자원을 소유하는가?
수명: 언제 생성·재생성·취소·정리되는가?
흐름: 입력이 어떻게 눈에 보이는 결과가 되는가?
증거: 어떤 테스트나 기기 관찰이 동작을 증명하는가?
함정: 그럴듯한 어떤 구현이 어떤 조건에서 실패하는가?
```

Compose에서는 recomposition, Activity 재생성, process death를 명확하게 구분한다. callback에서는 등록하고 해제하는 주체를 찾는다. coroutine에서는 소유 scope와 취소 시점을 찾는다. Navigation에서는 API를 설명하기 전에 관련 back stack 변화를 그린다.

## 주도권을 빼앗지 않고 검토하기

사용자가 작성한 코드를 검토할 때는 다음을 따른다.

- 코드가 현재 표현하는 행동을 먼저 설명한다.
- 정확성 문제와 스타일 선호를 구분한다.
- 실패하는 테스트, lifecycle 상황 또는 구체적인 유지보수 비용을 근거로 든다.
- 가치가 가장 높은 수정 하나를 먼저 선택한다.
- 사용자가 드라이버라면 직접 수정하도록 요청한다.
- 불확실성을 인정하고 변경 가능성이 있는 API 지침은 공식 자료에서 확인한다.

근거가 없는 칭찬으로 문제를 가리지 않는다. 막연한 긍정보다 “이 테스트가 회전 후 상태 복원을 증명한다”처럼 구체적으로 피드백한다.

## 건강한 점검 지점

의도한 이유로 실패하는 테스트, 통과한 행동, 테스트가 통과하는 상태의 리팩터링, 기기에서만 검증할 수 있는 경계처럼 자연스러운 지점에서 멈춘다. 대화를 만들기 위해 빌드가 깨진 중간 상태에서 멈추지 않는다.

두 경로가 모두 실제로 유용할 때만 점검 지점에서 간결한 선택지 하나를 제공한다. 예를 들어 UI 작업을 계속할지, 대칭적인 오류 사례를 사용자가 구현할지 고르게 할 수 있다.
