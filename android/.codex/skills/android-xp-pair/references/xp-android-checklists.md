# 안드로이드 학습 작업을 위한 XP 체크리스트

현재 활동에 필요한 절만 읽는다.

## 사용자 스토리 다듬기

학습용 사용자 스토리는 화면에서 관찰 가능한 행동을 전달하면서 주요 개념 하나를 연습해야 한다. 내부 클래스나 레이어의 완성을 사용자 가치처럼 표현하지 않는다.

```text
<사용자 또는 운영자>로서
<관찰 가능한 기능>을 원한다.
<얻게 되는 가치>를 위해서다.
```

인수 조건은 구현이 아니라 구체적인 사례를 설명해야 한다.

```gherkin
시나리오: 불러오기 실패 후 재시도 성공
  조건 첫 번째 Repository 요청이 실패했다.
  만일 사용자가 재시도를 선택하면
  그러면 두 번째 요청을 수행하는 동안 로딩을 표시한다.
  그리고 결과 콘텐츠를 표시한다.
```

주요 플랫폼 경계를 둘 이상 새로 도입하거나, 서로 관련 없는 화면이 필요하거나, 한 번의 페어링 세션에서 의미 있는 Green 상태에 도달할 수 없다면 스토리를 나눈다. 화면에서 시작해 필요한 상태·데이터·플랫폼 경계까지 연결되는 하나의 수직 사례를 선호한다.

## 가장 저렴하면서 신뢰할 수 있는 테스트 고르기

outside-in 개발에서는 먼저 화면 수준의 acceptance check를 정한다. 가능하면 UI 테스트로 Red를 만들고, 환경상 실행할 수 없다면 구체적인 수동 관찰 절차를 기록한다. 아래 표는 그 바깥 행동을 구현하며 발견한 내부 정책을 가장 저렴하게 고정할 때 사용한다.

| 행동 | 먼저 사용할 테스트 | 더 높은 수준으로 올릴 조건 |
|---|---|---|
| 순수 정책, Reducer, 상태 머신 | Kotlin/JVM 단위 테스트 | Android 타입이 실제로 필요할 때 |
| ViewModel, Flow, coroutine 시간 제어 | Fake와 가상 시간을 사용한 JVM 테스트 | lifecycle·프레임워크 통합 자체가 학습 대상일 때 |
| Stateless Compose 렌더링과 동작 | Compose UI 테스트 | Navigation이나 시스템 UI가 참여해야 할 때 |
| Fragment/XML 상호작용 | 가능하면 JVM, 그렇지 않으면 Espresso | 실제 프레임워크 동작이 필수일 때 |
| Navigation과 back stack | route·상태 단위 테스트와 집중 Navigation 테스트 | deep link, 복원 또는 Activity 통합이 중요할 때 |
| Permission, Service, Telecom/Telephony callback | Fake 어댑터 계약 테스트 | 에뮬레이터·기기에서 공개 API 동작을 확인할 때 |
| 접근성, 큰 글자, adaptive layout | UI semantics·layout 검사 | 시각적 결과나 하드웨어 동작을 수동 확인해야 할 때 |

그럴듯한 회귀가 발생했을 때 실패하고, 실패 결과가 깨진 행동을 설명해주는 테스트가 가치 있다. 구현 호출을 그대로 따라 하는 테스트는 피한다.

## Red-Green-Refactor 점검

### Red

- 화면에서 사용자가 수행하는 동작과 관찰 결과가 테스트 이름과 assertion에 드러난다.
- 테스트 이름이 행동 하나를 표현한다.
- 설정이 잘못돼서가 아니라 그 행동이 아직 없어서 실패한다.
- 실패 메시지를 직접 확인했다.

### Green

- 화면에서 필요한 최하단 경계까지 하나의 실행 가능한 슬라이스로 연결됐다.
- 프로덕션 코드는 동작을 만족하는 가장 작고 일관된 구현이다.
- 관련이 있다면 취소, 소유권, lifecycle 경계가 명확하다.
- 관계없는 아키텍처를 추가하지 않았다.

### Refactor

- 의미 있는 변경마다 테스트가 계속 통과한다.
- 이름이 사용자 행동이나 도메인 의도를 표현한다.
- 가능하면 Android 프레임워크 코드를 좁은 경계 뒤에 둔다.
- 중복의 형태를 이해한 뒤에만 제거한다.

## 학습 작업의 완료 정의

- 사용자 동작이 화면에서 시작해 필요한 데이터 또는 플랫폼 경계까지 끊김 없이 연결된다.
- 자동화 테스트나 기록된 수동 검사로 인수 조건을 증명했다.
- 집중 테스트가 통과하며, 위험에 비례하는 넓은 빌드·테스트 검사도 통과한다.
- 작업과 관련된 empty, loading, error, cancellation 또는 restoration 행동을 검토했다.
- 변경 내용에 의도하지 않은 생성 파일이나 관계없는 정리가 없다.
- 사용자가 입력에서 출력까지 추적하고 상태 소유자를 말할 수 있다.
- 의도적으로 남긴 제약 하나와 다음 작은 스토리가 보인다.

## 세션 노트 형태

세션 노트를 남기는 작업이라면 근거 중심으로 작성한다.

```markdown
# Day XX — <작은 결과>

## 사용자 스토리와 인수 조건
## Red: 예상한 실패와 그 이유
## Green: 최소한의 동작
## Refactor: 설계 개선
## 배운 안드로이드 사고 모형
## 명령과 검증 근거
## 바로잡은 실패 또는 오해
## 의도적으로 남긴 제약
## 기억을 꺼내보는 질문과 다음 연습
```

대화 전체가 아니라 원인과 관찰 결과를 기록한다. 도움이 된다면 저장소 파일에 링크한다.
